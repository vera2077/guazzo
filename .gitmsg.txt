fix: sec-r10 — never decode an unmeasured header, and put the Setup inside the release manifest

Four edges from the round-10 security review.

decodeImageFile sniffed PNG/JPEG/GIF/BMP/WebP and then, when the sniff returned
null, decoded anyway and checked the size afterwards. A JPEG with enough APPn
segments before its SOF (or a format the sniffer does not know) reached
WebView2's decoder first — a 30000² frame is ~3.6 GB. Every picture format the
editor advertises has a readable header, so a file whose dimensions cannot be
established before decoding is now refused by name instead of decoded.

The native open dialog capped files at 256 MB but the page refuses JSON above
192 MB; the Rust side read and base64-encoded the file before the page could
say no, peaking over 1 GB for a file that is never imported. The native cap is
now 128 MB, below every page-side budget.

A .cube without a LUT_3D_SIZE line was split into millions of rows before the
"no size" error, because the early abort was gated on knowing the size. The row
cap now applies regardless, and the split itself is bounded.

The Setup exe is the artifact winget installs, and it sat outside
release/<version>/ — not in RELEASE.json, not in SHA256SUMS.txt, not checked by
verify-asset. build-setup now copies the exe and its sidecar into the release
folder, adds the hash to the manifest and the checksum list, and verify-asset
checks the Setup whenever the manifest lists it. Signing remains opt-in
(RELEASE_REQUIRE_SIGNED=1) because this repository has no certificate: a
fail-closed default would make every local release impossible, and the honest
fix for an unsigned project is a visible unsigned flag, not a gate nobody can
pass.
