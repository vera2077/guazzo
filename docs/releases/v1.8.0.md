# 1.8.0 — Colour Lookup

Load a `.cube` 3D table and apply it as a live adjustment layer.

## What you can do now

- **Layer ▸ New Adjustment Layer ▸ Colour Lookup**, then **Load .cube…**.
  The dialog reports what it read — `Loaded "warm-film.cube" — 33×33×33 samples.` —
  or the parser's own complaint, with the line number.
- OK stays refused until a table is loaded. A lookup layer with no table would
  change nothing, and a layer that changes nothing is a layer that lies.
- The table is stored in the project file, so reopening a document does not ask
  for the file again, and it round-trips through PSD as a `3dlut` record.

## What is refused, and why

- 1D `.cube` tables (curves) are refused with "use Curves instead" — they are a
  different record, and mapping one onto the other would guess.
- Abstract and device-link ICC profiles are admitted, not guessed: the importer
  says what it dropped.
- A cube whose row count does not match its own `LUT_3D_SIZE`, or whose domain is
  malformed, is refused with the line number rather than read truncated.

## Verification

- `63 test files / 665 tests` green, 85 pins, smoke and the deterministic
  single-file build.
- The smoke run opens the dialog, confirms OK is refused with no table, loads a
  2×2×2 swap cube through the real file input, and reads the saved project back
  to find `lookup.size === 2` and the original file name. Removing the refusal
  turns exactly those assertions red.
- `.cube` stores red varying fastest; the first implementation read the table
  transposed and its own test caught it (`expected [255,0,0], got [0,0,255]`).

## Limits

No ICC-profile lookup (only `.cube`), no 1D curves as lookup, and the arithmetic
is float trilinear per pixel — a 65³ table is the largest accepted.
