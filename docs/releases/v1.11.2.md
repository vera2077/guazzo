## Guazzo 1.11.2

Dragging a picture in from Explorer did nothing, and this is why.

Tauri installs its own drag-drop handler over WebView2's, which turns the native
file drag into a Rust-side event (`tauri://drag-drop`). The page therefore never
received an HTML5 `drop` for a file dragged in from Explorer: the OS painted the
copy cursor — that part is the native handler working — and then nothing
happened, because the JavaScript handler that places the image was never called.

- The window is now built with `disable_drag_drop_handler()`, the API whose own
  documentation says it "is required to use HTML5 drag and drop APIs on the
  frontend on Windows since we replace the drag drop handler of WebView2".
- With the native handler off, `drop` reaches the page with real `File` objects,
  and the routing that shipped in 1.11.0 finally runs: canvas places the picture
  as a layer, tab bar opens it as a project, anything else opens by path.

### Why the tests did not catch it

The smoke fires the DOM `drop` event directly, so it tested the routing and the
placement but not whether the shell ever delivers the event. That gap is now a
pin: `scripts/pins.mjs` fails if `src-tauri/src/main.rs` stops calling
`disable_drag_drop_handler()`, and the probe that removes the call turns it red
(1 failed of 86).

### Verification

- 66 test files / 682 tests, 86/86 pins, gate green.
- The exe was rebuilt and its manifest/window code recompiled; the pin guards the
  configuration, which is the part a headless test cannot exercise.

If a future build wants Tauri's native drag-drop events instead, it must route
`tauri://drag-drop` itself — turning the handler back on without that listener
restores exactly this bug.
